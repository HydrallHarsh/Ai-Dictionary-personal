Part 01

The shape of lib/

Eight files, four tiers, one direction of flow. Learn the tiers and you can guess where any new code belongs.

Everything in lib/ is not a component. That is the whole selection rule. A component's job is to produce markup; a lib/ module's job is to produce data or a decision. This split matters more than it sounds, because it is what lets the same function be called from a server page and a browser component without either one knowing about the other.

The eight files sort into four tiers, and imports only ever point downward in this picture:

What each tier is allowed to do

TierFilesAllowed toNever
Access supabase/static, supabase/server, supabase/client Build a configured database connection Know what a post is
Shape blog-data, pipeline-stats Query, validate, turn rows into typed objects Know how anything looks
Derive archive, markdown, source-hues, utils Compute display facts from typed objects Touch the network
Render app/**, components/** Produce markup Compute a fact it could have been given
Why the direction matters

Because markdown.ts imports nothing, it can be called from anywhere — a server page, a client component, a test, a script. The moment it imported a Supabase client, calling it from the browser would drag database code into the browser bundle. A module's import list is its deployment surface. The comment at the top of source-hues.ts says this outright: it lives in lib/ rather than beside the archive component because a server page and a client component both need it, and importing it from the client module would pull that whole graph server-side.

One file breaks the tiers on purpose: api.ts talks to your FastAPI backend rather than Supabase, and is called from browser components. Part 11 covers it separately, including where it is weaker than the rest.

Part 02

TypeScript in one sitting

Everything you need to read the rest of this document. Each item appears in the real code, so you meet it here and recognise it later.

TypeScript is JavaScript plus labels describing what each value is. The labels are erased before the code runs — the browser never sees them. Their only job is to let a checker tell you, before you run anything, that you are about to use a value in a way that cannot work.

The five things that are 90% of it

1 — Annotations

the basic formvalue: Type
const EXCERPT_LENGTH = 180;              // inferred as number
function excerpt(text: string) { … }        // parameter annotated
function monthKey(time: number): string { } // return annotated

You rarely annotate variables. TypeScript infers them: it knows 180 is a number without being told. You do annotate function parameters, because a function can be called from anywhere and there is nothing to infer from.

2 — Object types

frontend/lib/archive.ts:21a shape with a name
export type ArchiveEntry = {
  slug: string;
  title: string;
  time: number | null;      // a union — see below
  difficulty: string | null;
};

Read type X = { … } as "from now on, ArchiveEntry means an object with exactly these fields". Passing an object missing slug is now an error at the call site, not a crash at 3am.

3 — Unions, and the null union in particular

A | B means "either an A or a B". The single most valuable use in this codebase is T | null, because it makes absence part of the type:

time: number | null  — a timestamp, or explicitly "no date"

Once a field is number | null, TypeScript refuses to let you do arithmetic on it until you have checked for null. That single rule is what mechanically enforces the "never render a lie" principle from Volume I — the compiler will not let you forget the absent case.

4 — Literal unions

frontend/lib/pipeline-stats.ts:31a typo becomes a compile error
export type Granularity = "week" | "month";

The type is not string — it is those two strings and nothing else. Write "weekly" and the editor underlines it immediately. This is one of TypeScript's genuinely delightful features and it costs nothing.

It is also what keeps the parse honest at the far end of the wire. This value arrives from the database inside untyped JSON, and the file converts it with payload.granularity === "week" ? "week" : "month". A value the union does not allow cannot get in, so nothing downstream has to defend against one.

5 — Optional vs nullable

WrittenMeansIn this repo
tags?: string[]The key may be missing entirelyPostContentPayload — the JSON blob may not have it

The distinction is worth internalising. ? describes the shape of data you were handed. | null describes a decision you made. archive.ts uses | null for difficulty because deciding "this post is ungraded" is an act, not an accident.

The four operators you will see constantly

OperatorReads asFires when
a ?? bnullish coalescinga is null or undefined only
a || blogical ora is any falsy value: 0, "", false, null…
a?.boptional chainingreturns undefined instead of throwing if a is nullish
x!non-null assertion"trust me, not null" — disables the check
?? versus || is a real bug source

Consider a count of zero. count ?? 0 keeps the zero. count || 0 also gives zero — fine. But likes || "unknown" turns a genuine 0 likes into the string "unknown", because 0 is falsy. The rule: use ?? when the fallback is for absence, and || only when you truly want every falsy value handled the same way.

blog-data.ts:184 gets this right — posts.find(…) ?? null, because find returns undefined when nothing matches and we want to convert that specific case. Meanwhile archive.ts:139 deliberately uses ||: title?.content || post.metadata?.title || "Untitled" — here an empty string should fall through to the next option, which ?? would not do.

The one to be suspicious of

x! tells the compiler to stop checking. It appears exactly twice in this codebase, both in lib/supabase/client.ts:

process.env.NEXT_PUBLIC_SUPABASE_URL!,
process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,

Compare with static.ts, which checks the same two variables and throws a named error if either is missing. The ! version fails later and more confusingly — somewhere inside the Supabase library, with a message that does not mention your environment file. The explicit check is the better pattern, and client.ts is the file that has not caught up.

Two things that look like magic but are not

as const

frontend/lib/source-hues.ts:27 · Navbar.tsx:44freeze into literals
const LINKS = [
  { href: "/blog", label: "Blog" },
] as const;

Without as const, TypeScript infers { href: string; label: string }[] — a mutable array of general strings. With it, every value becomes its exact literal and everything is readonly. You get two benefits: accidental mutation is an error, and the literal types flow into anything derived from the array. It costs nine characters.

Indexed access: (typeof X)[number]

frontend/lib/source-hues.ts:29derive the type from the data
export type SourceHue = (typeof HUE_CLASSES)[number];

Read it right to left. typeof HUE_CLASSES is "the type of that array". [number] is "index it with any number" — i.e. one element. So SourceHue is exactly one hue object, and it was never typed by hand.

This is the pattern to remember: write the data, derive the type. Add a fifth hue slot to the array and SourceHue updates itself. Had the type been hand-written, the array and its type could drift apart silently.

Generics, briefly

A generic is a type with a blank in it, filled at the call site.

Map<string, number>  — a Map whose keys are strings and values numbers
Set<string>  — a Set of strings
Promise<BlogPost[]>  — a promise that will produce an array of BlogPost

You will mostly use generics rather than write them. The one place this codebase writes its own is types/content.ts: Block<T = unknown> — a block whose data field type is filled in later, defaulting to unknown.

The unknown / any distinction

any

"Stop checking this value."

Every operation on it is allowed. The lack of checking spreads to everything it touches, silently, forever.

unknown

"I do not know what this is."

No operation is allowed until you narrow it with a check. The uncertainty is contained at the boundary.

They look like synonyms and behave as opposites. unknown is the correct type for anything arriving from outside your program — a JSON column, a network response, a parsed file.

Part 03

blog-data.ts — the boundary

213 lines whose entire job is converting untrusted database JSON into objects the rest of the app can trust. The most type-heavy file in the repo, and the best one to learn from.

This file sits on the seam between two worlds. On one side: a Postgres jsonb column, which can legally contain anything — an object, an array, a number, null. On the other: the rest of the frontend, which wants to write post.blocks[0].data.content without checking four things first.

The pattern for a boundary like this is always the same three steps, and they are worth naming because you will need them again:

  1. Describe what you hope for as a type, with everything optional.
  2. Check at runtime, once, at the door.
  3. Produce a strict type that downstream code can rely on unconditionally.

Step 1 — the hopeful type

frontend/lib/blog-data.ts:14everything optional on purpose
type PostContentPayload = {
  title?: Partial<TitleBlock["data"]>;
  summary?: string;
  description?: string;
  slug?: string;
  generated_image?: string | null;
};

Two pieces of syntax here are worth unpacking, because together they are one of the neatest lines in the codebase.

TitleBlock["data"] is indexed access on a type. It means "the type of the data field of TitleBlock". Not the value — the type. So instead of re-declaring the title's fields here, this file points at the single definition in types/content.ts. Change it there and this follows.

Partial<…> is a built-in type transformer: it takes a type and makes every field optional. So Partial<TitleBlock["data"]> means "the title block's data shape, but assume nothing is actually present".

Why this combination is correct

TitleBlock["data"] alone would be a lie: it declares content: string as required, and the database absolutely contains rows without it. Re-typing the fields by hand would create a second source of truth that drifts. Partial<TitleBlock["data"]> is the honest version — same fields, no promises — and it stays in sync automatically.

Step 2 — the type predicate, the pattern to actually memorise

frontend/lib/blog-data.ts:30a function that teaches the compiler
function isPostContentPayload(
  value: unknown
): value is PostContentPayload {
  return Boolean(
    value && typeof value === "object" && !Array.isArray(value)
  );
}

Look at the return type. It is not boolean — it is value is PostContentPayload. This is a type predicate, and it is the mechanism by which runtime checks become compile-time knowledge.

What it does: after if (isPostContentPayload(row.content)), inside that block, TypeScript treats row.content as a PostContentPayload instead of unknown. You have converted a runtime fact into a static one. Nothing else in the language does this.

Read the body carefully — it is doing three jobs
  • value && rejects null. Necessary because typeof null === "object" in JavaScript, a 1995 bug that will outlive us all.
  • typeof value === "object" rejects strings, numbers, booleans.
  • !Array.isArray(value) rejects arrays. Also necessary, because arrays are objects too, and ["a"].title is undefined rather than an error — so an array would sail through and produce a post with every field empty.

Three clauses, three distinct JavaScript quirks, one line each. This is what a boundary check looks like when it is taken seriously.

The honest limitation

This predicate checks that the value is an object. It does not check that summary is a string. So the type is a promise the code only partially keeps — which is exactly why the next step never trusts individual fields either. asString(content.summary, "…") re-checks each one at the point of use. Belt and braces, and appropriate: a full schema validator (Zod, Valibot) would be the alternative, and is worth considering if this file grows.

Step 3 — the field-level guard

frontend/lib/blog-data.ts:34default parameter + truthiness
function asString(value: unknown, fallback = "") {
  return typeof value === "string" && value.trim()
    ? value
    : fallback;
}

fallback = "" is a default parameter: callers may omit it. TypeScript infers its type as string from the default, so no annotation is needed.

Note value.trim() in a boolean position — a string of only spaces trims to "", which is falsy, so whitespace counts as absent. That is a deliberate content decision expressed as three characters, and it is why no article renders a title of one space.

The line that ties it together

frontend/lib/blog-data.ts:162the map/filter idiom
return (data ?? [])
  .map((row) => mapRowToBlogPost(row))
  .filter((post): post is BlogPost => post !== null);

Three things happen in three lines.

data ?? [] — Supabase returns data: T[] | null. Coalescing to an empty array means every following line can assume an array exists. This is the "make the absent case boring" move, and it appears throughout the codebase.

.map(…) — mapRowToBlogPost returns BlogPost | null: null for a row whose content failed the check. So after the map you hold (BlogPost | null)[]. Bad rows are skipped, not thrown — one malformed row does not empty the archive.

.filter((post): post is BlogPost => …) — and here is the trick. A plain .filter(p => p !== null) removes the nulls at runtime but TypeScript still types the result as (BlogPost | null)[], because it cannot see inside the callback. Annotating the callback as a type predicate tells it: things that survive this filter are BlogPost. The result is BlogPost[], with no cast and no lie.

The archive.ts one is worth seeing, because it is what makes the date span safe:

frontend/lib/archive.ts:200same pattern, different type
const times = entries
  .map((entry) => entry.time)              // (number | null)[]
  .filter((time): time is number => time !== null);  // number[]

  ? { from: …Math.min(...times), to: …Math.max(...times) }

The predicate is what permits the next line, and the times.length > 0 guard is what stops Math.min() of nothing returning Infinity — which would have printed a span of "January 1970 — …". The type system caught the first problem; a human had to catch the second.

Deriving a type from a function: Awaited<ReturnType<typeof f>>

frontend/lib/blog-data.ts:134never hand-write what you can derive

Peel it from the inside:

Why bother? Because queryBlogPosts must accept either client, and the Supabase client type is a large generic monstrosity nobody wants to type by hand. Deriving it means the day you change how a client is built, this type follows silently. createStaticClient is not async, so it needs no Awaited — and that asymmetry is itself information about the two functions.

The same trick, one tier up

app/blog/page.tsx:31 does it again for a value: let archive: ReturnType<typeof buildArchive> | null = null;. The page needs a variable that can hold "the archive or nothing" before the try block, and it gets the archive type without importing Archive at all. Both spellings are fine; this one has one less import.

The memoised export

frontend/lib/blog-data.ts:178one query per render pass
export const getPublicBlogPosts = cache(async (): Promise<BlogPost[]> => {
  return queryBlogPosts(createStaticClient());
});

cache() from React wraps a function so that within a single server render, calling it repeatedly runs the body once and hands everyone the same result. The article page needs this: it calls getPublicArticle for the page body and React separately calls generateMetadata, which needs the same corpus. Without cache, that is two full queries for one page view.

Note what cache is not: it is not a cross-request cache, and it holds nothing between page views. It is a per-render memo, and that is exactly the scope you want — broader would mean serving stale data.

Neighbour lookup by index arithmetic

frontend/lib/blog-data.ts:200free adjacency
const posts = await getPublicBlogPosts();
const index = posts.findIndex((post) => post.slug === slug);
if (index === -1) return null;

// The query orders newest first, so the preceding entry is the newer one.
return {
  post: posts[index],
  newer: posts[index - 1] ?? null,
  older: posts[index + 1] ?? null,
};

Getting the previous and next article costs no query at all — the ordered list is already in hand, so adjacency is just index ± 1. The ?? null handles the two ends: posts[-1] is undefined in JavaScript rather than an error, and the first article genuinely has no newer neighbour.

The comment earns its place. index - 1 being the newer post is only true because the SQL ordered descending; without that sentence the next reader has to go find the query to know whether the arrows are backwards.

Part 04

Three Supabase clients, and why

lib/supabase/ holds three files that all create a database client. That looks like duplication. It is not — each one exists because of a different constraint, and picking the wrong one changes how the page renders.

FileLinesRuns inKnows about youEffect on the route
static.ts30Server, build timeNothingRoute stays static
server.ts42Server, per requestReads cookiesRoute becomes dynamic
client.ts9BrowserSession in storagen/a — runs after load

The whole design turns on one Next.js fact: calling cookies() opts a route out of static generation. Not "might" — it is the mechanism by which Next decides. A cookie is per-visitor, so a page that reads one cannot be a single pre-built file.

Which means the innocent-looking act of importing the wrong client turns a page that could be served as flat HTML into one that runs a server render on every hit.

static.ts — the one the public pages use

frontend/lib/supabase/static.tsno cookies, therefore static
export function createStaticClient() {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const key = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;

  if (!url || !key) {
    throw new Error(
      "Supabase environment variables are missing…"
    );
  }

  return createSupabaseClient<Database>(url, key, {
    auth: { persistSession: false, autoRefreshToken: false },
  });
}

Three things to notice.

The explicit check earns a real error message. process.env.X is typed string | undefined — TypeScript will not let you pass it where string is required. There are two ways past that. This file checks and throws with a sentence a human can act on. The alternative is on the next page.

createSupabaseClient<Database> — the generic is doing all the work. Database is the generated type describing every table and column. Passing it means .from("posts") is checked against real table names, .select("slug, published_at") is checked against real columns, and the rows that come back are typed. Drop the <Database> and every query silently returns any — the code still compiles, and every typo becomes a runtime surprise.

persistSession: false is the point of the file. It tells the client: do not try to remember anyone. No session storage, no refresh timer. This is a read-only pipe for public data, and saying so explicitly is what makes it safe to call at build time.

client.ts — and the two ! assertions

frontend/lib/supabase/client.tsthe same problem, the shortcut answer
export function createClient() {
  return createBrowserClient<Database>(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!
  );
}
Same problem, worse failure mode

! is the non-null assertion: "trust me, this is not undefined." It silences the compiler and changes nothing at runtime. If the variable is actually missing, static.ts throws "Supabase environment variables are missing" and you fix it in a minute. This one passes undefined into the Supabase constructor and you get a network error about an invalid URL, three layers down, at some later moment.

These are the only two ! assertions in the frontend. That is not an accident of taste — it is a rule that held everywhere except here.

server.ts — the cookie bridge

frontend/lib/supabase/server.tsasync, because cookies() is
export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient<Database>(url, key, {
    cookies: {
      getAll() { return cookieStore.getAll(); },
      setAll(cookiesToSet) {
        try {
          cookiesToSet.forEach(({ name, value, options }) =>
            cookieStore.set(name, value, options)
          );
        } catch {
          // Called from a Server Component. Middleware refreshes the
          // session, so this is safe to ignore.
        }
      },
    },
  });
}

This is the one that makes "who is logged in" work on the server. Supabase does not know about Next.js cookies, so you hand it two functions and it calls them when it needs to read or write the session.

The catch with only a comment in it looks like swallowed-error sloppiness, and normally would be. Here it is correct and the comment is the proof: Server Components are not allowed to set cookies (the response headers are already gone by then), so setAll throws in exactly one predictable situation, and middleware has already refreshed the session anyway. An empty catch is acceptable only when a comment explains which specific throw it is absorbing. One without that sentence is a bug in waiting.

catch { with no binding is also worth naming — modern JavaScript lets you omit (error) when you are not going to look at it. Small thing, but it signals intent: this is not a dropped variable, it is a deliberately unexamined error.

The wiring, in one sentence each
  • blog-data.ts imports both server clients and accepts either via the PostsClient union — so the query logic is written once.
  • The public exports (getPublicBlogPosts, getPublicArticle) hard-wire createStaticClient, which is what keeps /blog and /blog/[slug] static.
  • client.ts is imported only by AuthContext — the browser side, where a session genuinely exists.
Part 05

markdown.ts — a state machine you can read

333 lines, no dependencies, six exports. The most algorithmic file in the repo and the one with the most to teach about writing loops that are correct rather than merely usually-right.

Every function here exists because generated markdown is not trustworthy markdown. The model writes a title even though the page already has one. It writes summaries of wildly varying length. It leaves handoff notes in the body. Each of those is a real defect, and each gets one focused function.

The two-flag line loop

sanitizeArticleMarkdown walks the document one line at a time carrying exactly two pieces of state:

frontend/lib/markdown.tsthe shape of the loop

  const line = lines[i];

Why the fence check must come first

A code block can contain the line # TODO. That is a comment in a shell script, not a heading. Any rewriting rule that runs before the fence check will happily demote it to ## TODO and corrupt the sample. Ordering here is not style — it is correctness, and it is the reason the two continues sit at the top of the loop before any other rule gets a look.

inFence = !inFence is a toggle: fences come in pairs, so the same line type both opens and closes. Two lines of code for a rule that would otherwise need a counter and an off-by-one bug.

The regexes, and reading them without fear

NamePatternMatches
ATX_HEADING/^(#{1,6})\s+(.*)$/# Title through ###### Title

The last one is the interesting one, and it reads backwards from how it looks. (?!…) is a negative lookahead: "the next thing must not be any of these." So PARAGRAPH_TEXT says — starting at the beginning of the line, this must not be indentation, not a bullet (- * +), not a blockquote (>), not a table row (|), not a numbered item (1. or 1)) — and then must be a non-space character.

In plain words: a line of actual prose, not a list item and not part of a structure. That definition matters because setext headings are underlined paragraphs, and you cannot tell "heading text" from "bullet" without it.

The look-back that makes setext work

To know whether ===== is underlining a heading, you have to look at the line above — but a blank line may sit between them in the source. So the loop walks backwards past blanks until it finds real text, and only then decides. This is the single fiddliest piece of logic in the file, and it exists because markdown has two entirely different heading syntaxes and the generator uses both.

The stateful closure: createSlugger()

frontend/lib/markdown.tsa function that remembers
/** Create one per render pass. Never share one across documents. */
export function createSlugger() {
  const seen = new Map<string, number>();

  return function slugify(text: string) {
    const base = … // lowercase, strip punctuation, hyphenate
    const count = seen.get(base) ?? 0;
    seen.set(base, count + 1);
    return count === 0 ? base : `${base}-${count}`;
  };
}

A function that returns a function, where the inner one can still see seen after the outer one has finished. That is a closure, and it is how JavaScript does private state without a class.

The problem it solves is concrete: an article with two sections both called "Overview" would produce two elements with id="overview", and the table-of-contents link would only ever reach the first. The counter turns the second into overview-1.

Why the doc comment is not optional

Because the state lives in the closure, a slugger shared between two articles would number the second article's headings as if they were continuations of the first — overview-1 on a page with only one Overview. It would look like an intermittent bug and be miserable to find. Map<string, number> is the generic to read here: keys are strings, values are numbers, and TypeScript enforces both.

Recursive narrowing: nodeText(node: unknown)

frontend/lib/markdown.tswalking a tree you were not handed a type for
function nodeText(node: unknown): string {
  if (typeof node === "string") return node;
  if (typeof node === "number") return String(node);
  if (Array.isArray(node)) return node.map(nodeText).join("");
  if (node && typeof node === "object" && "props" in node) {
    …
  }
  return "";
}

This is the narrowing ladder in its purest form. The parameter is unknown, so at the top of the function you can do nothing with it at all — not even read a property. Each if buys one capability, and only inside that branch.

"props" in node is the in operator used as a type guard: after it, TypeScript knows node has a props key and will let you read it. Note the ordering again — node && before typeof node === "object", because typeof null lies, exactly as in blog-data.ts. The same three-clause dance, in a different file, for the same reason.

Final return "" rather than a throw: an unrecognised node contributes nothing to the text and the walk continues. A heading with one odd child still gets a slug.

The global-regex trap

frontend/lib/markdown.tsthe line that looks redundant and is not
HANDOFF.lastIndex = 0;
let match: RegExpExecArray | null;
while ((match = HANDOFF.exec(text)) !== null) {
  last = match;   // keep walking; we want the final one
}
A real footgun, not a style preference

A regex with the g flag carries a cursor (lastIndex) between calls. Because HANDOFF is declared once at module scope, the second call to this function would resume scanning from wherever the first one stopped — and quietly miss the match. Resetting lastIndex to 0 before the loop is what makes the function idempotent. This bug is invisible in a single test and appears the moment two articles render in one pass.

The loop deliberately keeps going to find the last match rather than the first, because a handoff note is appended at the end of the body — and an article that mentions the phrase earlier should not have its middle chopped out.

standfirst() — encoding an editorial rule as an invariant

const STANDFIRST_TARGET = 230 — aim for this
const STANDFIRST_MAX = 340 — never exceed this

The function accumulates whole sentences until adding the next would pass the target, then stops. Two decisions are worth stealing:

  • The first sentence is always included, even if it alone blows past MAX. Cutting mid-thought to satisfy a number produces a fragment that means nothing; an over-long first sentence is at least true.
  • Two constants, not one. A single limit forces a binary choice at the boundary. A target plus a ceiling lets the code prefer a natural stop and only hard-cut when there is no other option.

readingTime() — the return type is the design

function readingTime(markdown: string): string | null

Not number. Not string. string | null, because below MIN_WORDS = 40 there is no honest answer — "1 min read" on a stub is a fabricated fact. The smallest interesting file in the repo. It assigns a colour to a publication, and does it in a way that survives filtering, matches across pages, and costs nothing.

frontend/lib/source-hues.tsthe whole file, minus comments
const HUE_CLASSES = [
  { dot: "bg-hue-1", text: "text-hue-1", wash: "bg-hue-1-wash" },
  { dot: "bg-hue-2", text: "text-hue-2", wash: "bg-hue-2-wash" },
  { dot: "bg-hue-3", text: "text-hue-3", wash: "bg-hue-3-wash" },
  { dot: "bg-hue-4", text: "text-hue-4", wash: "bg-hue-4-wash" },
] as const;

export type SourceHue = (typeof HUE_CLASSES)[number];

export function hueFor(source: string): SourceHue {
  let hash = 0;
  for (let i = 0; i < source.length; i++) {
    hash = (hash * 31 + source.charCodeAt(i)) >>> 0;
  }
  return HUE_CLASSES[hash % HUE_CLASSES.length];
}

Trick 1 — derive the type from the data

export type SourceHue = (typeof HUE_CLASSES)[number];

Read it inside-out. typeof HUE_CLASSES is the type of the array. [number] is indexed access with a number, which for an array type means "the type of any element". So SourceHue is exactly { dot: "bg-hue-1"; text: …; wash: … } | { dot: "bg-hue-2"; … } | … — the union of the four literal shapes.

The alternative is to hand-write the type:

Hand-written — two things to keep in sync 
type SourceHue = {
  dot: string; text: string; wash: string;
};
Derived — one thing, always in sync 
type SourceHue =
  (typeof HUE_CLASSES)[number];

The derived version is not just shorter. Add a ring field to the objects and the hand-written type is now silently wrong — you can no longer read hue.ring even though it exists. The derived one already knows. Write the data, derive the type is the single highest-value TypeScript habit in this file.

Trick 2 — as const is what makes it work

Without as const, TypeScript widens the array to { dot: string; text: string; wash: string }[] — the literal strings become plain string, and the derived type loses everything specific. as const does two things: it freezes the values to their literal types ("bg-hue-1", not string) and it marks the array readonly, so nobody can .push() a fifth hue at runtime.

Trick 3 — hash the name, not the position

The obvious implementation is index-based: first source gets hue 1, second gets hue 2. It has a bug you would only find by using the page. Filter the archive down to three sources and the survivors renumber — every dot changes colour under the cursor. And a source's colour on the archive would not match its colour on the article page, because the two pages have different lists.

Hashing the name fixes both by construction. Colour follows the entity, not its position. Same name in, same slot out, on every page, under every filter, forever.

The arithmetic, briefly

hash * 31 + charCodeAt(i) is the classic string hash (31 is prime, which spreads values well and is cheap because x*31 is a shift and a subtract). >>> 0 is an unsigned right shift by zero — it does not move any bits, it coerces the result to a 32-bit unsigned integer. Without it, repeated multiplication overflows into negative numbers, and -7 % 4 is -3 in JavaScript, which would index HUE_CLASSES[-3] and return undefined. That would crash on hue.dot. One three-character operator is the difference.

Four slots, more than four sources

Collisions are guaranteed and the file's own header comment says so. That is acceptable here because of a rule worth generalising: the colour is never the only carrier of the information. Every dot has the source name printed beside it — ArchiveIndex.tsx:148, :162, :292 — and every dot is aria-hidden="true", so assistive technology reads only the name.

The hue is a scanning aid for "those two rows are the same publication", not an identifier. Nothing is gated behind telling hue 2 from hue 4, which means a collision degrades the experience slightly rather than breaking it.

Why this lives in lib/ and not next to the component

ArchiveIndex.tsx is a client component; the article page is a server component. Both need hueFor. If it were exported from the client module, importing it from the server page would drag that whole "use client" graph along. A dependency-free file in lib/ can be imported from either side — which is the same reasoning as Part 01's tier rule, applied to 39 lines.

Why the counting moved into the database

Not for the round-trip count. That was a bonus. The real reason is that the old version could only ever have worked by accident.

Row-Level Security answers with an empty array, not an error

raw_api_data — the table every “read” figure is counted from — has RLS enabled and no policy at all. In Postgres that combination is a closed door, and PostgREST reports a closed door as an empty room: status 200, data: [], error: null. A count request comes back Content-Range: */0.

That is indistinguishable, in code, from a table that is genuinely empty. Every guard in the old file tested error, and error was null. It would have counted zero articles read and reported complete success.

So why did the homepage ever show real numbers? Because the build was not using the public key. frontend/.env sets NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY to an sb_secret_ value, and a secret key runs as service_role, which bypasses RLS entirely. The figures were right and the mechanism was a security bug — the one filed as handle this first in Volume I. Fixing that bug on its own would have silently zeroed every read count on the landing page, while the keep counts, which come from the publicly-readable posts table, kept working. The chart would have drawn a kept segment taller than the column containing it.

The shape of this bug is worth more than the bug

Two correct-looking things — a query that returns no error, and a key that works — were covering for each other. Neither is wrong on its own. When a permission system reports absence rather than refusal, testing with the credentials you deploy with is the only test that means anything. The same page, built with the key it claims to use, produces different numbers.

The fix is a Security Definer function: SQL that runs with its author's privileges instead of the caller's. It counts rows the caller cannot see and returns only aggregates — never a row. The table stays shut, and the landing page still gets its proof.

frontend/lib/pipeline-stats.tscomposition: one guard per field, one exit
function asBucket(value: unknown): PipelineBucket | null {
  const row = asRecord(value);
  if (!row) {
    return null;
  }
  const start = asIso(row.start);
  const read = asCount(row.read);
  const kept = asCount(row.kept);
  const resolved = asCount(row.resolved);
  if (start === null || read === null || kept === null || resolved === null) {
    return null;
  }
  return { start, read, kept, resolved, partial: row.partial === true };
}

Two details in there are the difference between a guard that works and a guard that looks like it works.

start === null, not !start. A bucket where nothing was read has read: 0, and 0 is falsy — if (!read) would throw away every idle window in the series, which are precisely the windows the chart is careful to draw. Once a type is number | null, the only safe test is against null itself.

row.partial === true, not Boolean(row.partial) or a bare row.partial. The field is unknown, so the string "false" would pass a truthiness test. Comparing to true means anything that is not exactly the boolean becomes false, and the property lands in the object already typed — no cast needed.

The chart is a part-to-whole shape read left to right: a column missing from the middle does not omit a value, it misstates the trend, and nothing on screen indicates anything is absent. Same principle as drawing idle buckets at zero rather than skipping them. When individual values are read as a series, a partial series is worse than no series.

The transferable pattern

When a public surface needs a number derived from private rows, the choice is not between opening the table and doing without. A definer function is a third option: move the query to where the privilege already is, and let it return only the answer. Less data crosses the wire, the client keeps no read access it should not have, and a permissions mistake shows up as an exception instead of a plausible zero.

The filter: one useMemo

ArchiveIndex.tsx:177map groups, filter entries, drop empties
const groups = useMemo(() => {
  const term = normalise(query);
  if (!term && !source) return archive.groups;   // nothing to do

  return archive.groups
    .map((group) => ({
      ...group,
      entries: group.entries.filter((entry) => {
        if (source && entry.source !== source) return false;
        if (!term) return true;
        return (
          normalise(entry.title).includes(term) ||
          normalise(entry.excerpt).includes(term)
        );
      }),
    }))
    .filter((group) => group.entries.length > 0);
}, [archive.groups, query, source]);

useMemo caches the result and only recomputes when something in the dependency array changes. Without it, this runs on every render including ones caused by unrelated state elsewhere. With it, typing one character recomputes once.

{ ...group, entries: … } is the spread-and-override idiom: copy every field of group, then replace entries. The original object is never mutated, which is what React relies on to detect changes. Mutating group.entries in place would filter archive.groups itself — and since that array came from the server as props, the second search would search the already-filtered list and results would never come back.

The early return is a real optimisation, not decoration. With no query and no source there is nothing to compute, so returning the original array means useMemo hands back the identical reference and React skips re-rendering the whole list. The trailing .filter(group => group.entries.length > 0) is what stops empty month headers appearing above nothing.

The three-line comment that documents a decision

Search matches title and excerpt, deliberately not source name. The code says why: searching "TechCrunch" would return that publication's entire output, which is what the source pills are for. Two mechanisms doing the same job differently is worse than either alone — and this is exactly the kind of choice that gets "fixed" by the next person unless the reason is written down.

The functional updater

ArchiveIndex.tsx:272click the active pill to clear it
onClick={() =>

}

Passing a function to a setter gives you the current value as an argument. Here it makes the pill a toggle in one expression: clicking the selected source deselects it.

The alternative — setSource(source === item.name ? null : item.name) — reads the source variable captured when this render's closure was created. For a click handler that is almost always fine. The functional form is right unconditionally, and costs nothing, so it is the better default to build the habit around.

Array gymnastics for the chart order

ArchiveIndex.tsx:60reverse, then move one item to the end
const columns = [...groups].reverse();
const undated = columns.findIndex((group) => group.key === "undated");
if (undated !== -1) {
  columns.push(...columns.splice(undated, 1));
}

[...groups] before .reverse() matters: reverse mutates in place, so calling it on the prop would reverse the list the entry rows render from — the chart would fix itself and the list would silently invert. The spread makes a copy first. reverse, sort and splice all mutate; map, filter and slice do not. Knowing which is which prevents a whole class of React bug.

The second line pair is a small trick: splice(i, 1) removes one element and returns it as an array, so push(...that) puts it back at the end. Two lines to move "undated" to the far right, because it has no place on a time axis.

Why reverse at all? The list reads newest-first, but a time axis reads left to right, oldest to newest. Reversing here rather than in buildArchive means the chart runs forwards and the list still opens on the most recent entry — one data structure, two correct orderings, decided at the point of use.

The floor that keeps a small month visible

const height = Math.max(3, Math.round((count / max) * PLOT_H));

A month with one entry out of 120 would compute to under half a pixel and render as nothing — a gap in the row that looks like missing data rather than a small month. Math.max(3, …) guarantees a visible mark. The bar is no longer strictly proportional at the low end, which is the right trade: the number is printed above every bar anyway, so precision lives in the label and the bar carries the shape.

Announcing the result to a screen reader

A sighted user sees the list shrink. The same discipline runs through the pills: aria-pressed={active} states the toggle's condition, and the coloured dot inside each one is aria-hidden="true" so it is not announced as a meaningless image. Selection is carried by aria-pressed and the solid fill, never by the dot alone.

Two CSS details doing structural work
  • sticky top-16 on the month header, not top-0. The navbar is itself sticky at 64px; at top-0 the month header slid underneath it and a 100-entry group scrolled unlabelled.
  • [&>li:first-child>a]:border-t-0 — arbitrary-selector syntax targeting the first row's link. The month header already draws a rule; the first entry's own top border would double it into a 2px line. One class instead of a conditional prop threaded through EntryRow.

Part 11

api.ts — the odd one out

129 lines talking to the FastAPI backend for auth. Included honestly, because it was written under different assumptions than the rest of lib/ and comparing them teaches more than either file alone.

Everything covered so far reads from Supabase. This file posts to a separate Python service, and it shows: different error handling, different typing discipline, no type predicates anywhere.

The pattern it gets right

frontend/lib/api.tsinterfaces for request and response shapes
const API_URL = process.env.NEXT_PUBLIC_API_URL || "http://127.0.0.1:8000";

interface LoginPayload { username: string; password: string; }
interface RegisterPayload { email: string; username: string; password: string; }
interface RegisterResponse { id: string; email: string; username: string; }

interface and type are near-interchangeable for object shapes. interface can be reopened and added to later; type can also express unions and intersections. This codebase uses type almost everywhere and interface only here — a stylistic split that follows the file's origin rather than any rule.

process.env.NEXT_PUBLIC_API_URL || "http://127.0.0.1:8000" is the third answer to the missing-env problem, after static.ts's throw and client.ts's !. A default is genuinely the right call here: local development should work with no configuration at all. Note it must be || and not ??, so that an env var set to the empty string also falls back.

The login: 204 by design

frontend/lib/api.tsform encoding, cookies included
export async function loginUser(payload: LoginPayload): Promise<boolean> {
  const body = new URLSearchParams();
  body.set("username", payload.username);
  body.set("password", payload.password);

  const res = await fetch(`${API_URL}/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body,
    credentials: "include",
  });
  …
}

Three details that are each load-bearing.

URLSearchParams rather than JSON, because FastAPI's OAuth2PasswordRequestForm expects form encoding. Send JSON and you get a 422 that reads like a validation bug in your own code.

credentials: "include" is what lets the browser store the session cookie the backend sets. Omit it and login "succeeds" — 204, no error — and the user is still anonymous on the next request. A silent failure with a success status, and one of the harder auth bugs to spot.

Promise<boolean> as the return type is right for the caller's question. The endpoint returns 204 No Content by design, so there is no body to parse and nothing to hand back except whether it worked.

The cast that breaks the file's own discipline 
const data = await res.json();
return data as RegisterResponse;

as is an assertion, not a check. It tells the compiler "treat this as RegisterResponse" and verifies nothing at runtime. If the backend renames username to user_name, TypeScript keeps reporting data.username: string and the value is undefined — a type error the type system has been instructed to ignore.

Compare blog-data.ts, which faces exactly the same problem with database JSON and answers it with a type predicate plus asString per field. Same category of untrusted input, two very different levels of care. The fix is a predicate like isRegisterResponse; the point of naming it here is that as on the result of res.json() is always a promise you cannot keep.

Why this section exists

Not to score points. This file predates the rebuild and was not part of it. It is here because the contrast is the lesson: the difference between blog-data.ts and api.ts is not knowledge of TypeScript — both were written by someone who knows the language — it is whether the boundary was treated as a boundary. The three that matter most, if you only keep three

1 — Put uncertainty in the type

string | null, BlogPost | null, number | null. Every one of these appears because the honest answer is sometimes "unknown", and the type makes every caller deal with it. This is the mechanism behind "never render a lie" — it is not discipline, it is the compiler refusing to let you skip the case.

2 — Check once, at the boundary

isPostContentPayload + asString + mapRowToBlogPost means untrusted JSON is validated in one file. Everything downstream — archive.ts, the components, the pages — works with BlogPost and never checks anything. Validation scattered through twenty components is how you get twenty slightly different definitions of "valid".

3 — Do the work where it happens once

Date formatting, alias folding, excerpt cutting, sorting, grouping — all in buildArchive, on the server, before any component exists. The client component receives correct data and spends its code on interaction. This is why the archive is 366 lines of UI rather than 900 lines of UI-and-repair.

Syntax glossary

Every piece of TypeScript and JavaScript notation used in this codebase, in one place, each with the file you can go and read it in. Skim it now; come back when a line stops making sense.

Type notation

x: string
An annotation. Only needed where TypeScript cannot work it out itself — parameters, and variables declared without a value.
type X = { … }
Names an object shape. Erased at build time; it constrains code, it does not become code.
interface X { … }
Near-identical to type for object shapes, and can be reopened to add fields later. Only api.ts uses it here.
A | B
A union: one or the other. string | null is the workhorse — it makes absence part of the type.
"a" | "b"
A literal union: not any string, only those exact values. Granularity in pipeline-stats.ts:31.
x?: T
The key may be missing entirely. Describes data you were handed.
x: T | null
The key is always present; the value may be nothing. Describes a decision you made. Not interchangeable with the line above.
Array<T> / T[]
The same thing. T[] is the convention in this repo.
Map<K, V>, Set<T>
Generic collections. Map<string, number> in markdown.ts's slugger and archive.ts's counters; a Set in SignalMeter.tsx:261 holding the two bucket dates that get a direct label, so the render asks has() once per column instead of comparing against both.
Promise<T>
What an async function returns. await unwraps it to T.
unknown
"A value, but no promises." You must narrow it before doing anything. The correct type for untrusted input.
any
"Stop checking this." Looks like unknown, does the opposite. Appears in this codebase only implicitly, in api.ts's untyped return.
T["key"]
Indexed access: the type of that field. TitleBlock["data"] in blog-data.ts:14.
(typeof X)[number]
The element type of an array value. The "derive the type from the data" move — source-hues.ts:29.
Partial<T>
Every field of T, made optional. Built in.
ReturnType<typeof f>
What f returns. app/blog/page.tsx:31.
Awaited<T>
Unwraps a promise type. Combined with the above in blog-data.ts:134.
value is T
A type predicate, as a function's return type. The bridge from runtime check to compile-time knowledge. blog-data.ts:30.
x as T
An assertion. Changes nothing at runtime and verifies nothing. Once in this codebase, in api.ts, and flagged in Part 11.
as const
Freeze to literal types and mark readonly. What makes source-hues.ts's derived type specific rather than string.
<T> at a call site
Supplying a generic explicitly: useState<string | null>(null), createClient<Database>(…). In both cases inference would give you something useless.

Four sentences worth keeping

The whole volume, compressed
  • If a value can be unknown, say so in the type — then the compiler makes every caller handle it, and you cannot render a lie by accident.
  • Validate once, at the boundary — a type predicate at the door beats defensive checks in twenty components.
  • Write the data and derive the type from it — two hand-maintained descriptions of the same thing will drift, and the drift is silent.
  • Do the work where it happens once — on the server, before the component exists, so the UI is about interaction rather than repair.
