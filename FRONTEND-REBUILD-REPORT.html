Part 01

Read this first

What this document is, who it is for, and the one idea that explains most of the choices in it.

This is not a changelog. It is an explanation. Everything here answers the same two questions in a loop: what did the code do before, and why is the new version better? Where a concept is needed to follow the answer — what a component is, what “server-rendered” means, why a colour needs two versions — the concept is explained in the same breath, from zero.

The parts are numbered because they build. Part 02 defines vocabulary the rest of the document uses without apology. Parts 03–08 are the logic: routing, data, architecture. Parts 09–12 are the design system. Parts 13–17 are the constraints, the bugs, and the honest list of what is still broken.

The one idea

If you remember a single sentence from this whole document, make it this one:

The governing rule

The interface must never show a number, a badge, or a label that the data does not actually support.

Not “should try not to”. Never. If the reading time was never measured, the page does not print a reading time. If the difficulty was never graded, no difficulty badge appears. If a count fails to load, the row disappears rather than showing a zero.

That rule sounds like an ethics statement, but in practice it is an engineering rule, and it is the reason for at least a third of the code described here. A default value like "5 min read" is a lie with a nice UI. Once you refuse to ship lies, you are forced to either measure the thing yourself or drop it — and “measure it yourself” is where a surprising amount of the new logic came from.

How to read the code samples

Every code sample is real code from this repository, not a simplification. The label above each one tells you the file it came from. If a sample is annotated, the grey italic lines are comments — notes for humans that the computer ignores.

Part 02

The words you need

React, Next.js, TypeScript and Tailwind explained from nothing, in the order they stack on top of each other.

The bottom layer: HTML, CSS, JavaScript

A web page is three things. HTML is the content and its structure — this is a heading, this is a paragraph, this is a link. CSS is the appearance — headings are 40 pixels and bold, links are blue. JavaScript is the behaviour — when you click this, open that.

Everything below is a tool for producing those three things. None of them replace the trio; they just stop you writing it by hand.

React: the page as a set of functions

Writing HTML by hand means copying the same navigation bar into every file. React's idea is that a chunk of interface should be a function that returns HTML. That function is called a component.

A component, at its simplestconcept
function Greeting() {
  return <p>Hello.</p>;
}

The HTML-looking syntax inside a JavaScript file is called JSX. It is not really HTML — a build step converts it to real JavaScript before the browser sees it — but you can read it as HTML and be right about what it produces.

Components take inputs, called props. A prop is just a function argument with an HTML-ish spelling at the call site:

Props are argumentsconcept
function Greeting({ name }) {
  return <p>Hello, {name}.</p>;
}

// used as:
<Greeting name="Harsh" />

That is the entire core of React. Components call other components, props flow downward, and the top-level component eventually describes the whole page. In this project, ArchiveIndex renders many EntryRow components, each handed one entry as a prop.

The other React concept you will meet here is state: a value a component remembers between clicks. When state changes, React re-runs the component function and updates only the parts of the page whose output changed. The archive's search box is state; so is whether the mobile menu is open.

Next.js: React plus everything React deliberately left out

React only knows how to turn components into HTML. It has no opinion about URLs, no way to fetch data on a server, no build system. Next.js is the framework that supplies all of it.

The two Next.js facts that shape this codebase most:

  • The folder structure is the URL structure. A file at app/about/page.tsx is the page at /about. No routing configuration exists anywhere in this project because there is nothing to configure.
  • Components can run on the server. This is the big one, and Part 03 is mostly about its consequences.

Server components vs. client components

In old React, every component ran in the visitor's browser. The browser downloaded an empty page plus a large JavaScript bundle, then built the page from scratch on the visitor's machine.

In modern Next.js, a component runs on the server by default. It executes on your machine (or your host), talks to the database directly, produces finished HTML, and sends that. The visitor's browser receives a real page. The component's code is never shipped to them at all.

A component only runs in the browser if it says so, with a line at the top of the file:

frontend/components/Navbar.tsx — line 1opt-in
"use client";

You need that line when a component uses interactivity: state, clicks, keyboard input, or anything that reads the browser's own environment. The navbar needs it (the mobile menu toggles). The article page does not (it is text).

Why this matters constantly

Every "use client" is a cost. That component's code, plus every library it imports, gets bundled and downloaded by every visitor. So the recurring question in this codebase is “can this stay on the server?”, and the answer is yes far more often than it looks.

Hydration is the word for what happens after: the server HTML arrives and renders instantly, then React's JavaScript loads and “attaches” to the existing HTML so the interactive bits start working. Text is readable before hydration. Buttons are not. That distinction decides several things later in this document.

TypeScript

TypeScript is JavaScript with labels on the values. Writing function readingTime(markdown: string): string | null declares that this function takes text and returns either text or nothing. If you later call it with a number, or forget to handle the “nothing” case, the compiler stops you before the code runs. That is why pnpm tsc --noEmit appears as a verification step throughout this rebuild — it is a whole class of bug caught without opening a browser.

Tailwind CSS

Instead of writing CSS in a separate file and inventing class names, Tailwind gives you tiny single-purpose classes you compose in the markup: flex means “lay children out in a row”, mt-5 means “margin-top, step 5”, text-muted-foreground means “use the muted text colour”. The advantage is that you can see an element's full appearance without hunting through stylesheets. The discipline it requires is Part 09.

The App Router, the three ways a page can be rendered, and the one-line trick that changed how articles are served.

What the root layout does

app/layout.tsx is 44 lines and does four jobs. It loads the typeface, it declares the light/dark theme provider, it draws the page frame, and it sets the <html lang="en"> attribute.

frontend/app/layout.tsxthe frame
<div className="mx-auto max-w-[1440px] min-h-screen
  bg-background border-x border-border shadow-2xl">

Read that as: centre the site, cap it at 1440 pixels wide, always at least a full screen tall, paint the theme background, draw a hairline down each side, and lift it off the surrounding page with a shadow. That single element is why the site reads as a document on a desk rather than edge-to-edge web app, at every screen size, on every route, without any page repeating the rule.

The typeface is loaded through next/font/google, which downloads the font at build time and serves it from your own domain. That matters for two reasons: no request to Google when a visitor loads the page, and no flash of the wrong font, because Next.js reserves the exact space the real font will take.

The three rendering modes

This is the single most important Next.js concept for understanding the decisions in Parts 04 and 07. Every route is rendered in one of three ways:

ModeWhen the HTML is builtCost per visitor
StaticOnce, at build timeZero. It is a file.
ISRAt build, then re-built on a timerZero, except for the one unlucky request that triggers a refresh.
DynamicOn every single requestA full render plus every database query, every time.

ISR stands for Incremental Static Regeneration, and it is the mode this site lives in. You opt in with one line at the top of a page file:

app/page.tsx · app/about/page.tsx · app/blog/[slug]/page.tsxISR
export const revalidate = 3600;

3600 seconds is one hour. It means: serve the stored HTML to everyone; if an hour has passed since it was built, quietly rebuild it in the background and serve the fresh copy from then on. Visitors always get an instant file, and the content is never more than an hour stale. For an archive that updates on a pipeline schedule, that is exactly the right trade — and it is one line per page.

The trick worth stealing

A dynamic route like /blog/[slug] with no generateStaticParams function is treated by Next.js as fully dynamic: responses come back Cache-Control: no-store, and every view of every article re-runs the full corpus query.

Declaring the function — even completely empty — opts the route into on-demand ISR instead. The first visitor to a slug pays for the render; the next hour of visitors get a cached file.

frontend/app/blog/[slug]/page.tsx — empty on purposeISR opt-in
export function generateStaticParams() {
  return [];
}

Why empty, rather than listing all 244 slugs? Because rendering one article costs one full-corpus fetch. Listing all of them means paying that cost 244 times during every build, to save the first visitor of each article a single query. That is the wrong trade, and the comment in the file says so, so nobody “fixes” it later.

Part 04

Where data comes from

Two database clients, one subtle rule about cookies that decides the whole caching strategy, and how the same query gets reused without running twice.

The cookie rule

Supabase is the database. Talking to it needs a client object. This project has two of them, and the reason is a rule that is easy to miss and expensive to get wrong:

The rule

If a route reads cookies(), Next.js must render it per-request. It has no choice — cookies are different for every visitor, so a cached page would be the wrong person's page. The route silently drops out of static generation and becomes dynamic.

The normal Supabase server client reads cookies, because that is how it knows who is logged in. So any page that used it became dynamic — including the homepage and the archive, whose content is identical for every visitor on earth.

The fix is a second client that never touches cookies:

frontend/lib/supabase/static.tscookie-free
export function createStaticClient() {
  const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const supabaseKey = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;

  if (!supabaseUrl || !supabaseKey) {
    throw new Error("Missing required environment variables: …");
  }

  return createSupabaseClient<Database>(supabaseUrl, supabaseKey, {
    auth: { persistSession: false, autoRefreshToken: false },
  });
}

persistSession: false and autoRefreshToken: false are the whole point: this client is explicitly not for logged-in users. It reads public rows and nothing else. And because it never asks for a cookie, the pages using it stay static.

So the split is:

Public content anyone can see
createStaticClient()
Anything about the logged-in user
createClient() — cookies

And in the data layer that shows up as one deliberately-named function:

frontend/lib/blog-data.tsthe public path
// Reading `cookies()` forces a route to render per-request. The post
// list is the same for everyone, so pages that only display it use
// this and stay statically generated with ISR.
export const getPublicBlogPosts = cache(async () => {
  return queryBlogPosts(createStaticClient());
});

cache(): the same query, asked twice, run once

Notice the wrapper: cache(...). This is a React function, and it solves a problem that appears the moment you fetch data inside components.

The article page needs the corpus twice: once to render the article, and once in generateMetadata to produce the browser tab title and the social preview. Two separate functions, both needing the same rows. Without cache(), that is two identical database round-trips per render.

cache() memoises for the duration of one render pass: the first call runs the query, the second gets the stored result, and the cache is discarded when the render finishes. No stale data, no manual plumbing, no passing the data down through props just to avoid a second fetch.

The shape the frontend actually wants

The database does not store rows in the shape a page wants to render. So one function does the translation, once, at the boundary — and this is the part that replaced an entire folder of components (Part 05).

frontend/lib/blog-data.ts — makeBlocks()the boundary
// One row in → a small typed array out. A `title` block, a
// `summary` block, optionally an `image` block, and the body
// as an `explanation` block.

One detail inside it is worth pulling out, because it is a good example of the governing rule from Part 01 doing real work. The date field is normalised, not defaulted:

Why dates get rewritten here

The generator writes date in whatever shape the source used. So the archive was rendering raw ISO strings (2026-07-12) directly next to formatted ones (April 23, 2026) in the same list — two date formats in one column, which reads as a bug even though every value was correct.

Fixing it in the component would mean fixing it in every component that ever shows a date. Fixing it at the boundary means every consumer downstream gets one format, for free, forever.

Neighbours without a second query

An article page shows “older” and “newer” links at the bottom. The naive approach is two extra queries: one for the row before, one for the row after. Instead:

frontend/lib/blog-data.ts — getPublicArticle(slug)zero extra queries
return { post, newer, older };
// The query is newest-first, so posts[index - 1] is the NEWER one
// and posts[index + 1] is the older one. Same ordered list the
// archive already uses — no second fetch, and the ordering can
// never disagree with the archive's ordering.

That last clause is the real benefit. Two separate queries could drift apart — different sort, different filter, and suddenly the article's “newer” link points somewhere the archive lists as older. Deriving both from one list makes the disagreement impossible rather than unlikely.

Part 05

The block teardown

You had built one component per content type. Ten files became three, and this is the full argument for why that is an improvement rather than a simplification.

What was there before

The old article renderer was a folder, components/blocks/, containing ten files:

frontend/components/blocks/ — deletedbefore
block-renderer.tsx        ← the switch statement
code-block.tsx            ← server half
code-block-client.tsx     ← client half
difficulty-block.tsx
example-block.tsx
explanation-block.tsx
header-block.tsx
image-block.tsx

summary-block.tsx

The design was reasonable on paper. Content arrives as a list of typed blocks; each type gets a component that knows how to draw it; a dispatcher looks at block.type and picks the right one:

the pattern, reconstructedbefore
switch (block.type) {
  case "title":          return <HeaderBlock … />;
  case "summary":        return <SummaryBlock … />;
  case "explanation":    return <ExplanationBlock … />;
  case "code":           return <CodeBlock … />;
  case "image":          return <ImageBlock … />;
  case "example":        return <ExampleBlock … />;
  case "related_topics": return <RelatedTopicsBlock … />;
  case "diagram":        return <DiagramBlock … />;
}

Problem one: five of the nine branches were unreachable

The content pipeline emits, per article, exactly three things: a title with its metadata, a summary, and one string of Markdown containing the entire body.

That is it. No code blocks arrive as blocks. No images arrive as blocks. No diagrams, no examples, no related-topics arrays. Those five block types had a TypeScript interface, a React component, and a branch in the dispatcher — and across 244 articles, not one of them ever ran.

Why dead branches are worse than they look

They are not free. They are code you maintain, code the bundler processes, code a reader has to check before concluding it is irrelevant, and code that quietly rots — because it is never exercised, nobody notices when a refactor breaks it. Five components that had never rendered were, in effect, five confident-looking lies about what the system does.

Problem two: spacing had nine owners

This is the subtler failure and the one that actually shows on screen. Each block component set its own margins — ExplanationBlock decided the gap above a paragraph, ImageBlock decided the gap around a picture, CodeBlock decided its own.

So the vertical rhythm of an article — whether it reads as one continuous document or as a stack of unrelated cards — was an emergent property of nine independent decisions made at nine different times. There was no single place to go and change it. Making paragraphs breathe more meant editing several files and hoping the result was consistent.

Problem three: one concept, two files, for a technical reason

code-block.tsx and code-block-client.tsx were one component split in half solely to cross the server/client boundary from Part 02. Syntax highlighting needed browser JavaScript, so the highlighting half needed "use client", so the server half existed to wrap it. That is architecture spent on plumbing, not on the product.

What replaced it: three pieces

Before

10 files. 9 block types. 2 dispatch layers. 5 branches that never ran. Spacing decided in 9 places. Link handling repeated per component.

After

3 pieces. 1 dispatch site. Spacing decided once. Link handling defined once, structurally impossible to forget.

Piece 1 — lib/blog-data.ts narrows once at the boundary. Instead of a page receiving arbitrary blocks and asking “what is this?”, the data layer produces exactly the three shapes the page uses. The page then picks what it needs by name:

frontend/app/blog/[slug]/page.tsxafter
const titleBlock = post.blocks.find((b) => b.type === "title");
const summaryBlock = post.blocks.find((b) => b.type === "summary");
const explanationBlock = post.blocks.find((b) => b.type === "explanation");

No switch. No dispatcher. No unreachable branch, because you cannot write a branch for a type you never look up.

Piece 2 — ArticleBody.tsx has one override map. The body is Markdown, so a Markdown renderer draws it. Where the default output needs changing, you override that one HTML element, in one object, in one file:

frontend/components/article/ArticleBody.tsxafter
<ReactMarkdown
  remarkPlugins={[remarkGfm]}
  components={{
    h1: headingRenderer(2, slugify),
    h2: headingRenderer(2, slugify),
    h3: headingRenderer(3, slugify),
    table: …, th: …, td: …,   // scrollable on phones
    a: …,                     // external-link safety
    img: …,                   // Next.js image optimisation
  }}
>

Piece 3 — the prose plugin owns vertical rhythm. One string of classes, in one exported constant, defines the spacing and typography of every element an article can contain:

frontend/components/article/ArticleBody.tsx — PROSE_CLASSone owner
"prose-h2:mt-14 prose-h2:mb-4 …"
"prose-h3:mt-10 prose-h3:mb-3 …"
"prose-p:leading-relaxed prose-li:leading-relaxed"
"prose-blockquote:border-l-2 prose-blockquote:border-brand …"

To make articles breathe more, you edit one line. Every element moves together, because they are all described in the same place, in the same units, at the same moment.

The three benefits, stated plainly

1. Adding a content type is now zero frontend work

If the pipeline starts emitting code fences or tables inside the Markdown body, they render correctly the day they arrive. No new component, no new type, no new branch. The renderer already understands Markdown; the pipeline just has to write it.

2. One dispatch site instead of two layers

Previously a change to how headings look meant: find the block type, find the component, find where the dispatcher passes props to it, check the client/server split. Now it means editing headingRenderer. The path from “I want to change this” to “here is the line” is one step.

3. Link safety is structurally impossible to forget

Article text is machine-generated from third-party sources, so outbound links are untrusted. Every external link must get rel="noopener noreferrer nofollow". Under the old design that rule had to be remembered in every component that could contain a link. Now there is exactly one place a link can be created, and the rule lives there:

frontend/components/article/ArticleBody.tsxone rule, one place
a: ({ href, children, ...props }) => {
  const external = Boolean(href && /^https?:/i.test(href));
  return (
    <a href={href}
      // Untrusted outbound links from generated text.
      {...(external
        ? { target: "_blank", rel: "noopener noreferrer nofollow" }
        : {})}
      {...props}>{children}</a>
  );
},

Those three attributes each do a specific job. noopener stops the opened page from being able to script your tab. noreferrer stops it learning where the click came from. nofollow tells search engines you are not endorsing the destination — correct, since a machine chose it.

What was kept, and why

The types file, types/content.ts, survived. It still describes all eight block shapes even though only three are produced, because it is the contract with the pipeline: if the generator starts emitting code blocks tomorrow, the shape is already agreed. Its one edit was a real fix:

frontend/types/content.tstightened
/**
 * `unknown` rather than `any` for the default: every interface
 * below narrows `data` to a concrete shape, so nothing actually
 * relies on the default being assignable in both directions.
 * `any` here silently disabled checking for any future `Block`
 * used without a type argument.
 */
export interface Block<T = unknown> {
  id: string; type: string; data: T;
}

For a beginner: any means “stop checking this value”. unknown means “I do not know what this is, so you must check before using it”. They look similar and behave oppositely. any is a hole in the type system that spreads silently to everything it touches; unknown is a question the compiler forces you to answer.

A correction worth recording

During the cleanup I searched for imports of types/content.ts with a glob pattern of lib/**/*.ts, got no results, and reported the file as orphaned. That was wrong: lib/blog-data.ts imports from it on line 4. Ripgrep's ** does not match files sitting directly in the folder, only files in subfolders. The reliable form is grep -rn --include=*.ts <dirs> with no glob at all. A tool that answers “no matches” when it means “I did not look there” is the most dangerous kind.

Part 06

Derive, never store

Four fields the interface used to read from the database and now computes itself — because the stored values were absent, wrong, or quietly invented.

Part 01's rule — never render a claim the data does not support — produced a repeating pattern. Each time, the sequence was the same: a field looked reliable, the corpus was actually counted, the field turned out to be mostly missing, and the frontend started measuring the thing instead of trusting it.

Reading time

estimated_time is absent on 178 of 244 entries. The old data layer filled the gap with the string "5 min read". So three quarters of the archive printed a number nobody had measured, in a column that looks measured — the worst possible combination, because it is confidently wrong and impossible to distinguish from the correct rows.

The body text, however, is always there. So it is counted:

frontend/lib/markdown.ts — readingTime()measured
const WORDS_PER_MINUTE = 220;  // adult silent reading, non-fiction
const MIN_WORDS = 40;          // below this the fetch fell back to a stub

const words = markdown
  .replace(/```[\s\S]*?```/g, " ")      // drop fenced code
  .replace(/`[^`]*`/g, " ")              // drop inline code
  .replace(/!?\[([^\]]*)\]\([^)]*\)/g, "$1") // links → their text
  .replace(/[#>*_~|-]/g, " ")             // strip markup chars
  .split(/\s+/)
  .filter((t) => /[\p{L}\p{N}]/u.test(t)).length;

if (words < MIN_WORDS) return null;   // ← nothing to measure: say nothing

Markup is stripped first or a code block would inflate the count with punctuation nobody reads word by word. And the function returns null — not "1 min read" — when there is genuinely no body. The caller drops the whole element. One rule, applied to every entry, true by construction.

Difficulty

Present on roughly a quarter of the corpus. The old code defaulted the rest to "beginner", which invents a grade the pipeline never assigned. Now an ungraded entry gets no badge at all:

frontend/lib/archive.tsabsence is a value
const graded =
  raw === "intermediate" || raw === "advanced" ? raw : null;

Note what this also fixes visually: because “beginner” was the default, almost every row wore a beginner badge, which made the badge meaningless as a scanning signal. Removing the invented ones turned a decoration back into information.

Source names

The ingest adapters record whatever a feed called itself. One publication therefore arrived under five spellings: Marktechpost, MarkTechPost, Marktech Post, MarktechPost, MarkTech Post. Five buckets for one source. The filter showed five near-identical rows, and each one understated the publication's real share of the archive.

frontend/lib/archive.ts — normaliseSource()fold the variants
const SOURCE_ALIASES = new Map([
  ["marktechpost", "MarkTechPost"],
  ["thenextweb",   "The Next Web"],
  ["techcrunch",    "TechCrunch"],
  ["newshub",       "NewsHub"],
]);

export function normaliseSource(raw) {
  const trimmed = (raw ?? "").trim();
  if (!trimmed) return "Unattributed";   // ← not "" and not "Unknown"
  const key = trimmed.toLowerCase().replace(/[^a-z0-9]/g, "");
  return SOURCE_ALIASES.get(key) ?? trimmed;
}

The key is built by lowercasing and deleting everything that is not a letter or digit, so all five spellings collapse to marktechpost before the lookup. A source with no alias entry passes through untouched — the map fixes known collisions rather than trying to guess at every name.

Repairing the Markdown itself

The generator's output has two consistent defects. Both were rendering as visible garbage, and both are now fixed in one pass before the text reaches the renderer.

Defect one: a duplicate H1. 175 of 244 bodies open with their own top-level heading, and it is never the headline the page displays. The page shows the source's headline; the body writes its own, differently worded. Rendering both gives the article two competing titles and two H1 elements — which is also an accessibility problem, since a document should have exactly one.

Defect two: stray underlines. In Markdown, a line of ===== under a line of text makes it a heading. But # Heading followed by ===== is not that: the # already closed the heading, so the underline renders as a paragraph of equals signs. The ----- version is worse — it renders as a horizontal rule, which is why the corpus was full of stray dividers sitting directly under headings. 147 of these across 244 documents.

frontend/lib/markdown.ts — sanitizeArticleMarkdown()the fence guard
// Inside a fence everything is verbatim — `# load the model` is a
// comment in someone's Python, not a heading, and `---` may be YAML.
if (FENCE.test(line)) { inFence = !inFence; out.push(line); continue; }
if (inFence)          { out.push(line); continue; }

That guard is the difference between a repair and a corruption. A text-transforming function that does not understand code fences will happily rewrite the inside of someone's code sample.

The pass is careful in three more ways, and each one is a judgement call rather than a rule:

  • A real underline — one sitting directly below paragraph text — is a genuine heading, so it is kept. But it is rewritten into the ## form, because the table of contents is built by scanning for #-prefixed lines. Left alone, such a heading would appear in the body but be missing from the contents rail.
  • Three documents carry a second H1 further down. Those are demoted to H2, not deleted — they are real sections, and dropping them would lose content.
  • A --- with nothing above it to underline is a genuine divider and survives; a run of === in the same position is meaningless and is removed.

The standfirst

A standfirst is the large intro paragraph under a headline. The summaries average ~1,130 characters and restate the entire article. Set at display size, one ran thirteen lines of large serif covering the funding round, the investors, the founder's background and his Harvard exit — all of which the body then said again in its own sections. The reader reached the real opening having already read it.

So the page takes the first sentence or two and stops. The rest is not shown anywhere, because the body is the long version.

Part 08

Never render a lie

Failure handling as a design decision: why a missing count disappears instead of showing zero, and the database quirk that made every number on the homepage suspect.

null and 0 are different claims

Every figure on the homepage is counted from the database. When a count fails, the function returns null, and the interface drops the figure rather than printing 0.

The distinction is not pedantry. 0 says “we looked, and there is nothing”. null says “we do not know”. Printing zero when you mean “we do not know” converts a temporary infrastructure hiccup into a factual claim that the pipeline has processed nothing. An absent row is honest; a zero is not.

frontend/components/home/SignalMeter.tsxrefuse to draw
if (articlesRead === null || entriesKept === null) {
  return null;   // no readout at all, rather than a readout of nothing
}

// and, in the chart:
if (buckets.length < 2) {
  return null;   // "Without buckets there is no shape to draw,
                 //  and inventing one would make the page lie."
}
That first line used to read if (!articlesRead || !entriesKept)

Which is the same bug this section is about, committed by the code enforcing it. 0 is falsy in JavaScript, so a genuine zero — a real measurement — took the same branch as a failed read and deleted the entire readout, along with the source count and the start date that were sitting beside it and were perfectly fine.

Once a value is number | null, the truthiness test is no longer the null test. Writing === null costs six characters and is the only form that means what it says.

In React, return null from a component means “render nothing”. The rest of the page closes up around the gap automatically, because the layout is built with flex and grid gaps rather than fixed positions.

A third claim: “there is no answer yet”

Two states were not enough. The landing page showed a flat 0% keep rate for the two most recent months, which read as we rejected everything we read. Nothing had been rejected. The triage queue simply had not reached those items yet.

The rate was computed as kept / read, and an item sitting in the queue as pending or processing counted in the denominator as though it had been judged and refused. So the figure was not merely imprecise, it stated the opposite of the truth, and it grew more wrong the harder the ingest ran.

kept / read

Denominator: everything ingested. Anything not yet triaged is counted as a rejection.

A month the bot has not reached shows 0%.

kept / resolved

Denominator: the items the queue has finished with — succeeded, skipped or failed.

A month the bot has not reached shows no rate at all, and a line of prose saying why.

Independent degradation

The homepage has one further requirement: it is the one page that must never return a server error. So its two data sources fail separately:

Two ways a database can hand you a wrong number quietly

Both of these ship, because in both the wrong answer looks completely plausible.

One — PostgREST truncates silently

The API layer in front of the database enforces a server-side ceiling of 1000 rows per response and truncates past it without complaint. So .limit(10000) appears to work and returns 1000 rows. No error, no warning, no flag on the response.

Counting distinct sources from a truncated sample would understate the figure — and the understated figure would be a believable number, printed confidently on the homepage.

The defence is a paging loop with two independent stop conditions: a short page, which is the normal exit, and a hard ceiling, so a misbehaving API cannot spin forever. It lives in blog-data.ts:173, which still walks the table this way.

const MAX_PAGES = 50;      // a guard, so a bad response can't loop forever
Two — Row-Level Security reports a closed door as an empty room

raw_api_data, the table every “articles read” figure is counted from, has RLS enabled and no policy at all. A client holding the public key is not refused. It is told there are zero rows: status 200, data: [], error: null, and a count request returns Content-Range: */0.

Nothing in that response distinguishes “you may not look” from “there is nothing there”. Every guard in the old pipeline-stats.ts tested error, and error was null.

The homepage showed real numbers anyway, and the reason is the security issue in Part 17. frontend/.env supplies an sb_secret_ key, which runs as service_role and bypasses RLS entirely. Rotating that key to a genuine publishable one — the correct fix, on its own — would have zeroed every read count on the landing page without a single error appearing anywhere. The keeps, which come from the publicly-readable posts table, would have carried on working, so the chart would have drawn a kept segment taller than the column supposed to contain it.

The general shape

Two things that were each individually fine — a query returning no error, and a key that worked — were covering for one another. A permission system that reports absence rather than refusal can only be tested with the credentials you actually deploy. Building this page with the key it claims to use produces different numbers, and that difference is the test.

The token layer

Where every colour on the site is defined, why each one is defined twice, and how Tailwind turns a variable into a class name.

What a design token is

A token is a named colour rather than a literal one. Instead of writing #6366f1 in forty places, you define it once as --brand and refer to that name everywhere. Change the definition, and all forty places move together.

In CSS these are called custom properties, and they look like this:

  --hue-2: #b45309;  /* amber  */

  --hue-4: #e11d48;  /* rose   */

Why every token is defined twice

The site has a dark mode. The naive implementation is to invert everything — and it produces a bad dark mode every time, because colour does not behave the same on both grounds.

.dark {

  --border: #25252e;

  --brand-subtle: #1b1b2c;  --ring: #818cf8;

  --hue-3: #0f9d8e;  --hue-4: #ee4a67;

The concrete reason, with an example

A translucent accent needs a per-theme step. bg-indigo-500/25 — indigo at 25% opacity — sits visibly on white and is nearly invisible on black, because a 25% tint of a mid-tone over near-black barely moves off the background. The dark theme therefore uses a lighter indigo (#818cf8), not a darker one.

The same applies to the wash tokens: they sit at 7% in light and 11% in dark, because a wash has to climb further off pure black before it reads as a tint at all.

Those washes are computed rather than hand-picked:

--hue-1-wash: color-mix(in oklab, var(--hue-1) 7%, var(--background));

color-mix blends two colours in the browser. Because the wash is expressed as a percentage of the hue token, re-stepping the hue automatically re-derives the wash — you cannot end up with a teal panel behind indigo text. oklab is the colour space: mixing in it keeps perceived lightness even, where the older sRGB mixing muddies mid-blends.

Tailwind v4: turning a variable into a class

Defining --brand does not by itself give you a bg-brand class. Tailwind v4 wires that up with a block at the top of the stylesheet:

frontend/app/globals.cssthe bridge
@import "tailwindcss";
@plugin "@tailwindcss/typography";
@custom-variant dark (&:is(.dark *));

@theme inline {
  --color-brand: var(--brand);
  --color-hue-1: var(--hue-1);

The naming is the mechanism: register --color-brand and Tailwind generates bg-brand, text-brand, border-brand, ring-brand, and every opacity variant of each. The @custom-variant line defines what dark: means — here, “inside an element carrying the .dark class”, which is what the theme provider toggles on <html>.

The payoff is that almost no component ever writes dark: at all. bg-brand is correct in both themes because --brand resolves differently in each. Dark mode is handled in one file, not sprinkled across fifty.

The quirk that made an accent system necessary

Why nothing uses --primary

In this project --primary is pure #000000 in light and #ffffff in dark. It is not a colour; it is ink. So bg-primary gives a black button, and there is no way to get an accent out of it.

That is why --brand and the four --hue-* tokens were added as a separate layer rather than by re-defining --primary. Repointing --primary at indigo would have turned every existing black button, every ink-coloured heading and every default border indigo at once. The new tokens sit alongside and are opted into.

Four hues, each with a defined role; a hash function instead of a counter; and the contrast arithmetic that decided two specific shades.

You asked for “subtle colours, not too flashy”. The way that request was met was not by choosing quiet colours — it was by giving every colour a job, and refusing to use it anywhere else. Colour that means something reads as considered even when it is saturated; colour used decoratively reads as noise even when it is pale.

Colour follows the entity, never its rank

Here is the failure mode this avoids. Assign colours by list position — first source gets hue 1, second gets hue 2 — and then filter the archive down to three sources. The survivors move up the list, so they change colour. TechCrunch was teal a second ago and is indigo now. The reader's mental map is destroyed by an interaction that was supposed to narrow it.

The fix is to derive the colour from the source's own name:

frontend/lib/source-hues.tsstable by construction
export function hueFor(source: string): SourceHue {
  let hash = 0;
  for (let i = 0; i < source.length; i++) {
    hash = (hash * 31 + source.charCodeAt(i)) >>> 0;
  }
  return HUE_CLASSES[hash % HUE_CLASSES.length];
}

A hash turns text into a number. The same text always produces the same number, so the same source always lands in the same slot — on the archive index, inside a filtered view, and on the article page. Nothing is stored and nothing has to be kept in sync.

Three implementation notes worth reading, because each answers an obvious objection:

  • Why >>> 0? It forces the running total back into an unsigned 32-bit integer, so the hash cannot overflow into a negative number and produce a negative array index.
  • Collisions? Expected — there are more than four sources and four slots. Acceptable, because the hue is never the only carrier: the source name is printed next to every dot, everywhere a dot appears. The colour is a scanning aid for “these two rows are the same publication”, not an identifier. Nothing is gated behind telling hue 2 from hue 4.
  • Why does it live in lib/? Because both a client component (the archive index) and a server component (the article page) need it. Importing it from the client module would drag that whole component graph onto the server — the Part 02 boundary showing up as a file-placement decision.

Part 12

The chart

The signal meter is the landing page's whole argument. Every encoding decision in it, and why it ships without a charting library.

The site's claim is “we read everything and keep the good part”. The meter is the evidence: one column per bucket, full height is everything read, the bright segment at the base is what was kept.

“Bucket” rather than “month” because the width is chosen from the data. Under ten weeks of history the buckets are weeks; past that they are calendar months. A monthly axis over three weeks of operation draws one column and calls it a trend, and a weekly axis over two years draws a hundred and four. The threshold is decided in SQL, travels with the payload as granularity, and the component reads it to pick its heading, its labels and its table header — so the chart cannot disagree with itself about what a column means.

One axis, always

Reads and keeps differ by roughly 80×. The tempting move is a dual-axis chart — reads on the left scale, keeps on the right — so both lines are visible. This is the single most common charting mistake, and it is a fabrication: the two scales are chosen by whoever made the chart, so any crossing, convergence or gap between the lines is an artefact of that choice, not something in the data.

Keeps are a subset of reads, measured in the same unit. So it is drawn as part-to-whole inside one column. No second scale exists, so there is nothing to misalign and nothing to misread.

One clock, or the shape means nothing

This is the correctness fix that mattered most, and it was invisible because the chart looked fine.

The two halves of every column used to come from different tables on different timestamps: read from raw_api_data.created_at, the moment an article was ingested, and kept from posts.published_at, the moment an entry went live. Those are two populations on two clocks. An article read in September and published in October was counted in two separate columns, so the bright segment in a column was not a subset of the column containing it — which is the only premise that makes a part-to-whole bar legitimate.

What that allowed

A keep rate above 100%, for a start — nothing in the arithmetic forbade it. And entries backfilled into posts ahead of the pipeline — most of the table, at the time — have no originating raw item at all, so they were counted as keeps against reads that were never made.

Every figure is now counted over one cohort on one clock: the raw item's own ingest timestamp, with the keep credited through the posts.raw_item_id foreign key back to the item it came from. An article read in September and published in October is a September keep. That is also the more useful question — of what we read then, how much survived — rather than what did we publish this month, which is a publishing schedule, not a filter.

The backfilled entries have no raw_item_id, so they are now absent from both halves rather than present in one. And the migration that introduced the queue stamped every pre-existing raw row status = 'skipped', last_error = 'pre-queue backlog'; those are reads the pipeline never actually performed, so the SQL excludes them from every figure it returns.

In flight is not rejected

Covered in full in Part 08: the rate's denominator is the decided population, not everything ingested, so a bucket the triage queue has not reached yet shows its volume and no percentage. Two consequences are visible in the chart itself.

A bucket whose window is still open is marked partial by the SQL and rendered at 60% opacity, with “(in progress)” in its readout. It is real data and it is not yet comparable to the closed buckets beside it, and that is a distinction the eye can carry without a legend entry.

Those buckets are also excluded from the caption's endpoints. The caption compares a first and last bucket, and an in-flight bucket's volume is not comparable to a finished one's — a week that is two days old always looks like a collapse in throughput.

Empty buckets are drawn, not dropped

The pipeline was idle for a stretch. Removing those columns would compress the time axis and imply continuous operation. A gap in the data is data.

This is now guaranteed on the database side rather than assembled in TypeScript: the SQL generates the full series of bucket edges with generate_series and left-joins the data onto it, so a window with no activity comes back at zero by construction. Previously each window cost two separate count requests, and an absent window was a bug waiting on someone to notice a missing column.

Labels are sparing

Only the two endpoints of the story carry a direct label. Axis ticks carry the values in between; the table carries all of them. A number printed on every column is the classic way to make a chart unreadable — the point of a chart is the shape, and if every value is labelled you have made a table with decorative bars.

The caption underneath is generated from the data rather than written:

frontend/components/home/SignalMeter.tsxa caption that cannot go stale
const caption = `Keep rate ${
  last.kept / last.resolved < first.kept / first.resolved ? "fell" : "rose"
} from … while the volume read each ${period} ${
  volumePhrase(first.read, last.read)
}.`;

The direction word is read off the data, not assumed. If next month's filter loosens, the caption says “rose”. A hardcoded “fell” would eventually become a lie that nobody notices, because captions are the last thing anyone re-reads.

The volume half had the same defect one layer down and it is worth spelling out, because it is the subtler version of the mistake. The verb was hardcoded to “grew” while the number was computed — so the first period the pipeline read less than it did at the start, the caption would have said “grew 0.5×”. Both halves of that phrase are now derived together in volumePhrase(), which reads the verb off the rounded multiplier and keeps the multiplier above 1 in both directions: “fell 2.0×” is the sentence, never “grew 0.5×”. A multiplier that rounds to 1.0 gets a third branch, “remained unchanged”, because “grew 1.0×” is not a sentence either. A generated number next to a hardcoded word is a lie with a delay on it.

${period} rather than the literal “month”, for the same reason: the buckets are weeks when the history is short, and the sentence has to say which.

Part 16

Practices that paid

The working habits behind everything above, each with the concrete thing it bought.

1. Comments explain why, never what

Read almost any file in this project and the comments are unusual: they are long, and none of them describe what the code does. const PAGE = 1000 does not get “the page size”. It gets the paragraph about PostgREST silently truncating.

The reason is that what is already in the code and cannot go stale, while why exists only in the head of whoever wrote it and evaporates in a week. Every comment in this codebase is answering the question a future reader will actually have: “why is it like this, and what happens if I change it?”

The practical payoff is that these comments are load-bearing. The one on countIn stops someone extracting the table names into constants and silently losing type checking. The one on the empty generateStaticParams stops someone “completing” it and adding 244 renders to every build. They are guardrails written in English.

2. Delete dead code, but ask before deleting the unrecoverable

Ten block components, a navigation-menu primitive, two image hosts, and a 58MB folder of screenshots came out. Dead code is not neutral: it is maintained, bundled, read, and eventually trusted by someone who assumes it runs.

But the deletion was split by recoverability. Tracked files are one git checkout away, so removing them is cheap and reversible. The 58MB of untracked screenshots and the ad-hoc scripts folder were gone forever if wrong — so those were confirmed with you first, and the confirmation named exactly what would survive (all 20 public/ assets, the favicon, the bot diagrams). Recoverability, not size, decides whether you need permission.

3. Verify by build and typecheck, not by looking

You said, plainly: “stop checking every small change, let me see the changes — just do the changes.” That was the right call and it changed the verification loop for the better. Screenshots after every edit are slow and prove almost nothing. Three commands prove a great deal:

the verification looprun in this order

pnpm tsc --noEmit      # every type, every call site, no output files
pnpm build             # does it compile, and which routes are static?

The build output is the most underused of the three. It prints a route table with a symbol per route — ○ static, ● prebuilt, ƒ dynamic. That table is how you catch a page silently falling out of static generation because something deep in its import graph started reading a cookie. It is a performance regression test you get for free on every build.

The pattern repeats everywhere once you look for it:

The contents rail and the article body both need anchor IDs, and they must agree exactly — including how a document with two “Conclusion” headings de-duplicates them into conclusion and conclusion-1. Two separate implementations would agree until the day they didn't, and then the contents links would point at the wrong sections. One shared createSlugger() makes disagreement impossible.

5. Count the corpus before trusting a field

Every “this field is unreliable” claim in this document is a number: 178 of 244 missing, 175 of 244 with a stray H1, 147 setext underlines, ~1,130 characters average, 10 summaries with a generator preamble. None of those were guesses.

This matters because the difference between “sometimes missing” and “missing three quarters of the time” is the difference between a default being reasonable and a default being a lie. You cannot make that call without counting.

6. Prefer the platform

<details> instead of a JavaScript accordion. CSS group-hover instead of a mouse-event handler. A real <button> instead of a clickable div. <ol> because the stages are ordered. Native elements are smaller, faster, accessible by default, and work before hydration — four wins for less code.

7. Write the trade-off down next to the decision

The archive's client-side filter is only affordable because of the excerpt trim. The empty generateStaticParams is a considered trade against 244 build-time renders. The chart's grey deliberately fails a contrast ratio and compensates with a table. Each of those is a decision someone could reasonably reverse — and each one carries, in the file, the sentence explaining what reversing it would cost.

The through-line

Almost every practice above is the same move: make the wrong thing hard to do by accident. One dispatch site means link security cannot be forgotten. One slugger means the rail cannot disagree with the body. Union-typed table names mean a typo is a compile error. Returning null means a missing value cannot be printed as zero.

Discipline that depends on remembering fails. Discipline built into the shape of the code does not.

A secret key under that name is published to every visitor.

Two steps, in order: rotate the key (assume the current one is compromised), then rename the variable so a secret is never again carried by a name that means “send this to the browser”. The value has not been printed in any report, log, or commit.

One thing changed since this was first written, and it removes a trap. The homepage used to read raw_api_data directly, and that table has RLS enabled with no policy — so those reads only ever succeeded because the secret key bypasses RLS. Rotating to a genuine publishable key would have fixed the security bug and silently zeroed every “articles read” figure on the landing page, with no error logged anywhere. The counting now goes through public.pipeline_stats(), which needs only EXECUTE, so the rotation is safe to do on its own. It has been verified end to end against a local stack with a real publishable key: the function returns its figures, the table itself still returns nothing, and the service-role-only functions still refuse the key outright.

Glossary

Every term this document used, defined in one line each. Ordered roughly by when you first meet it.

component
A function that returns a piece of interface. The unit React is built from.
JSX
The HTML-looking syntax inside a JavaScript file. Converted to real JavaScript at build time.
props
Inputs to a component. Function arguments with HTML-style spelling at the call site.
state
A value a component remembers between interactions. Changing it re-renders the component.
server component
Runs on the server, can query the database directly, ships no JavaScript to the browser. The default in Next.js.
client component
Opted in with "use client". Runs in the browser, needed for interactivity, costs bundle size.
hydration
The moment React's JavaScript attaches to server-rendered HTML and interactivity starts working.
App Router
Next.js's routing system where the folder structure under app/ defines the URLs.
dynamic segment
A folder named [slug]. One file serves every value of that URL segment.
static generation
Building a page's HTML once at build time and serving the same file to everyone.
ISR
Incremental Static Regeneration. Static, but automatically rebuilt on a timer. revalidate = 3600 means hourly.
dynamic rendering
Building the HTML fresh on every request. What reading cookies or search params forces.
generateStaticParams
Lists which values of a dynamic segment to prebuild. Declaring it empty still opts into on-demand caching.
generateMetadata
Produces the page title and description for the browser tab and link previews.
cache()
A React helper that runs a function once per render pass no matter how many times it is called.
Promise.all
Runs several async operations concurrently instead of one after another.
useMemo
Recomputes a value only when its listed dependencies change.
TypeScript
JavaScript with type labels, checked before the code runs.
any vs unknown
any disables checking and spreads. unknown forces you to check before using. Prefer unknown.
union type
A value restricted to an explicit set, e.g. "posts" | "raw_api_data". A typo becomes a compile error.
design token
A named colour or size defined once and referenced everywhere.
@theme inline
The Tailwind v4 block that turns a CSS variable into usable utility classes.
color-mix / oklab
A CSS function that blends two colours; oklab is the perceptually even space to blend in.
ΔE (delta E)
How different two colours look to a human. Target 8+ for adjacent categorical hues.
CVD
Colour vision deficiency. Protanopia, deuteranopia and tritanopia are the three simulated here.
contrast ratio
Legibility of text on a background. 4.5:1 for body text, 3:1 for large text.
categorical / sequential / diverging
The three colour jobs. Identity, magnitude, polarity. Never mix them up.
part-to-whole
Drawing a subset inside its total on one axis, instead of two series on two scales.
standfirst
The large introductory paragraph under a headline.
ATX / setext heading
The two Markdown heading forms: # Heading and text with ===== beneath it.
slug
The URL-safe version of a title, e.g. how-it-works. Also used for heading anchors.
ARIA
Attributes that describe meaning and state to assistive technology when HTML alone cannot.
sr-only
A class that hides an element visually while keeping it available to screen readers.
focus-visible
Shows a focus ring for keyboard navigation but not for mouse clicks.
PostgREST
The API layer in front of the Postgres database. Caps responses at 1000 rows, silently.
head request
Asking for a count without the rows. Immune to the row ceiling.
remotePatterns
The allowlist of hosts the Next.js image optimiser may fetch from.

The four sentences worth keeping

  1. Never render a claim the data does not support. Absence is a value; print nothing rather than a default.
  2. Ask whether it can stay on the server. The answer is yes more often than it looks, and every yes is bundle a visitor never downloads.
  3. Give every colour a job, and never use it for anything else. Then make sure removing all colour breaks nothing.
  4. Write down why, next to the code. What the code does is already visible; why it is like this is not, and it is what the next person needs.
